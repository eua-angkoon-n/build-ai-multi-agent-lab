## Brand Strategist

### Positioning ชัดไหม — Headline vs Tagline

Headline ปัจจุบัน "Programmer ที่สนใจ AI agents" **ทำหน้าที่เป็น description มากกว่า positioning statement** — บอกว่าเป็นใคร (โปรแกรมเมอร์) และสนใจอะไร (AI agents) แต่ยังไม่ตอบว่า "แล้วดีกับคนอ่านยังไง" ซึ่งสำคัญมากเมื่อ audience หลักคือ HR/ผู้จ้างงานและลูกค้าที่ scan หน้าเว็บไม่กี่วินาที

จุดแข็งที่ซ่อนอยู่ใน Bio คือมุม "สะพาน" — เป็นโปรแกรมเมอร์ที่ทำงานจริงอยู่แล้ว (จงสถิตย์) และกำลังเอา AI agents มาปรับใช้กับงานจริง ไม่ใช่แค่ผู้ที่ตามกระแส นี่คือ differentiator ที่ headline ควรสื่อออกมา แทนที่จะเป็นป้ายบอกความสนใจเฉยๆ

ข้อเสนอ: แยกบทบาทให้ชัด
- **Headline** = positioning สั้น กระชับ บอก value ต่อคนอ่าน เช่น แนวทาง "โปรแกรมเมอร์ที่เอา AI agents มาแก้ปัญหางานจริง ไม่ใช่แค่ของเล่นใหม่"
- **Tagline/รอง headline** = รายละเอียดเสริม เช่น เอ่ยถึง workflow / เครื่องมือที่เน้นลงมือทำจริง (learning by doing) ซึ่งตรงกับ Bio ย่อหน้าที่สอง

ตอนนี้ทั้งสองชั้น (headline + bio) พูดซ้ำกันเรื่อง "สนใจ AI agents" โดยไม่มีชั้นไหนที่ทำหน้าที่ตะโกน value proposition ให้คนอ่านเร็วๆ เห็นภายใน 3 วินาทีแรก

### Audience — เน้นอะไร

Audience มีสองกลุ่มที่ต้องการคนละอย่าง:

1. **HR / ผู้จ้างงาน** — สแกนหาสัญญาณความน่าเชื่อถือเร็วๆ: ทำงานจริงที่ไหน, สายงานชัดไหม, ทักษะจับต้องได้แค่ไหน ต้องระวังไม่ over-claim (ตรงกับที่ PROFILE เตือนไว้แล้วว่า "อย่า claim ความเชี่ยวชาญที่ยังไปไม่ถึง") แต่ความซื่อตรงแบบ "กำลังเรียนรู้" ต้องมาพร้อมหลักฐานว่าเรียนแบบมีระบบ (เช่น ลงมือทำโปรเจกต์จริง ไม่ใช่แค่อ่านตามกระแส) ไม่งั้นจะอ่านเป็นจุดอ่อนแทนจุดขาย
2. **ลูกค้า** — ต้องการรู้ว่าจ้างแล้วได้อะไร แก้ปัญหาอะไรให้ได้บ้าง กลุ่มนี้สนใจ "ผลลัพธ์" มากกว่า "เทคโนโลยีที่ใช้" — เนื้อหาเรื่อง AI agents ควรแปลงเป็นภาษาที่พูดถึงปัญหา/ผลลัพธ์ ไม่ใช่ศัพท์เทคนิคล้วน

ทั้งสองกลุ่มอ่านหน้าเดียวกัน ดังนั้นโครงสร้างเนื้อหาควรจัดลำดับ: เปิดด้วย value/ผลลัพธ์ (ดึงทั้งคู่) → ตามด้วยรายละเอียดเชิงเทคนิค/แนวทางการเรียนรู้ (ลึกขึ้นสำหรับคนที่สนใจจริง)

### 3 ข้อเสนอปรับโทน/ข้อความ

1. **เปลี่ยน headline จาก "สนใจอะไร" เป็น "ทำอะไรให้ใคร"** — ยกมุม "problem-first" ที่ระบุไว้ใน Brainstorm ขึ้นมาเป็นแกนหลักของ headline/hero แทนที่จะเก็บไว้เป็นแค่หนึ่งในสามมุมเล่าเรื่อง About เพราะมุมนี้ตอบโจทย์ทั้ง HR และลูกค้าได้ดีที่สุด

2. **ลดคำว่า "สนใจ" (interested in) ในทุกจุดที่เป็นไปได้** — คำนี้สื่อถึงสถานะ passive/ผู้เริ่มต้น ทั้งที่ Bio จริงๆ บอกว่ามีการลงมือทำและกำลังหาทางปรับใช้กับงานจริงอยู่แล้ว ควรใช้คำที่สื่อ active learning เช่น "กำลังลงมือปรับใช้" / "กำลังทดลองนำมาใช้กับงานจริง" ซึ่งซื่อตรงเท่ากันแต่ให้พลังงานต่างกันมาก และยังคุมโทนไม่ over-claim ตามที่ PROFILE กำหนดไว้

3. **ใส่สัญญาณ "งานจริง" ให้เจือจางลงมาถึง Hero/Interests แทนที่จะฝากไว้แค่ใน Bio** — เช่น ถ้ามีการ์ดโปรเจกต์ (ตาม Nice-to-have) ควรใช้ frame แบบ "ปัญหา → ลองใช้ AI agent แก้ยังไง → ได้อะไร" ตรงตามมุม Problem-first ที่ระบุไว้ใน Brainstorm อยู่แล้ว วิธีนี้ช่วยให้ทั้ง HR (เห็นทักษะเชิงประจักษ์) และลูกค้า (เห็นผลลัพธ์) ได้สัญญาณที่ต้องการโดยไม่ต้องเพิ่มเนื้อหาใหม่เกิน scope v1

## UX Critic

### โครงสร้างข้อมูล interests / contact พร้อมสำหรับ 4 หน้าหรือยัง

**Interests** — ใน PROFILE มีแค่ label 3 รายการ (AI Agentic, Web Dev, Data Analysis) ไม่มีคำอธิบายต่อรายการเลย ถ้าจะทำเป็นหน้า `Interests` แยกเดี่ยวตาม IA ที่ระบุไว้ (Home/About/Interests/Contact) ข้อมูลตอนนี้ **บางเกินไปสำหรับหน้าเต็มหนึ่งหน้า** — จะกลายเป็นแค่ 3 คำลอยๆ ไม่มี context ว่าแต่ละด้านกำลังทำอะไร ระดับไหน ใช้เครื่องมืออะไร ต้องขอข้อมูลเพิ่มอย่างน้อย 1-2 บรรทัดต่อด้าน ก่อนเข้า Lab 04 ไม่งั้นหน้านี้จะดูว่างและไม่มีเหตุผลให้คนอยู่นาน

**Contact** — มีแค่ email + github ไม่มี framing ว่าติดต่อเรื่องอะไรได้ (จ้างงาน / โปรเจกต์ / พูดคุยทั่วไป) ทั้งที่ Audience มี 2 กลุ่มที่ต้องการคนละอย่าง (ตรงกับที่ Brand Strategist ชี้ไว้) แต่ contact ไม่มีช่องทาง/ข้อความแยกสำหรับแต่ละกลุ่ม — ผู้เยี่ยมต้องเดาเองว่าควรเขียนอะไรไปในอีเมล

**ข้อมูลที่ขาดสำหรับ IA 4 หน้า**: ไม่มีรูปภาพ (ตามข้อห้าม) จึงต้องมี visual anchor อื่นแทนใน Hero/About เพื่อไม่ให้ดูโล่ง; Guestbook (nice-to-have, ตรง Lab 05) ยังไม่มีนิยาม data fields (ชื่อ/ข้อความ/วันที่) — UI ฝั่ง Claude ออกแบบไม่ได้จนกว่าจะรู้ schema ฝั่ง backend

### จุดที่ผู้เยี่ยมจะสับสน

1. **Interests vs About ทับซ้อนกัน** — Bio พูดเรื่อง AI agents อยู่แล้ว ถ้า Interests หน้าแยกพูดเรื่องเดียวกันซ้ำโดยไม่มีมุมต่างชัดเจน (About = เส้นทาง/เรื่องราว, Interests = รายละเอียดเชิงลึกแต่ละด้าน) คนจะรู้สึกเหมือนอ่านวนซ้ำและงงว่าทำไมต้องมี 2 หน้า
2. **ไม่มี CTA ชัดในหน้า Home** — ตอนนี้ scope คือ Hero + preview แต่ไม่มีระบุว่าอยากให้คนทำอะไรต่อ (อ่าน About? ดู Interests? ติดต่อ?) เสี่ยง bounce สูงโดยเฉพาะกลุ่ม HR ที่ scan เร็ว
3. **สอง audience ปนกันไม่มี wayfinding แยก** — HR อยากเห็นหลักฐานทักษะ/ความน่าเชื่อถือเร็วๆ ลูกค้าอยากเห็นผลลัพธ์ ถ้าคอนเทนต์ผสมกันไม่มี label/ลำดับที่ช่วยแต่ละกลุ่มข้ามไปจุดที่ตัวเองสนใจ จะต้องอ่านทั้งหน้าเพื่อหาสิ่งที่ต้องการ
4. **Contact ไม่มี expectation setting** — ไม่บอกว่าตอบกลับเร็วแค่ไหน หรือควรเขียนอะไรมา ทำให้คนลังเลก่อนกดติดต่อจริง โดยเฉพาะกลุ่มลูกค้าที่ไม่รู้จักมาก่อน

### ข้อเสนอ IA และ microcopy

**IA เสนอ (4 หน้า)**
- **Home** — Hero (headline + 1 บรรทัด value) → การ์ด preview 3 interests (ลิงก์ไปหน้า Interests) → CTA เดียวจบไปหน้า Contact
- **About** — Bio เต็ม (เรียงตามมุมเล่าเรื่องที่เลือกใน Brainstorm) เน้นเส้นทาง/บริบทงานจริงที่ จงสถิตย์
- **Interests** — ขยาย 3 ด้านเป็นการ์ดแยก แต่ละด้านมี 1-2 บรรทัดว่า "กำลังลงมือทำอะไรอยู่" ไม่ใช่แค่ชื่อหัวข้อลอยๆ
- **Contact** — email + github พร้อม microcopy สั้นบอกว่าเรื่องแบบไหนทักมาได้ และ (ถ้าทำได้) expectation เวลาในการตอบกลับ

**Microcopy ตัวอย่างสั้นๆ**
- Home hero (รอง headline): "กำลังลงมือปรับใช้ AI agents กับงานจริง ไม่ใช่แค่ของเล่นใหม่" — ใช้คำ active ตามที่ Brand Strategist เสนอ ไม่ใช้คำว่า "สนใจ"
- การ์ด Interests บน Home: ปุ่ม/ลิงก์ท้ายการ์ด "ดูว่าแต่ละด้านกำลังทำอะไรอยู่ →"
- หัวหน้า Contact: "สนใจร่วมงาน คุยโปรเจกต์ หรือแค่ทักทาย — ทักมาได้เลยที่อีเมลหรือ GitHub ด้านล่าง"
- Guestbook empty state (เผื่อทำใน Lab 05): "ยังไม่มีข้อความ — เป็นคนแรกที่ทักทายสิ"

## Devil's Advocate

### ความเสี่ยง (อย่างน้อย 5 ข้อ)

1. **ข้อมูลส่วนตัว/PII รั่วผ่านช่องทางอ้อม** — PROFILE ห้ามโชว์รูป/เบอร์/ที่อยู่/เงินเดือนตรงๆ แล้ว แต่ **email จริงถูกวางไว้เป็น plaintext ใน `docs/PROFILE.md`** (`euaangkoon.n@gmail.com`) และจะถูกดันขึ้นหน้า Contact แบบ mailto ตรงๆ — เสี่ยง scraping โดยบอทสแปม/harvester ทันทีที่ไซต์ index บน public web ควรพิจารณา obfuscate (เช่น `[at]`), ใช้ contact form แทน mailto ตรง, หรือใส่ `rel="nofollow"` + honeypot ถ้าจะทำฟอร์ม — เรื่องนี้ไม่มีใครในสองความเห็นก่อนหน้าพูดถึงเลย
2. **Guestbook = ช่องโหว่ที่ยังไม่มีเจ้าของด้าน moderation** — UX Critic เองก็ยอมรับว่ายังไม่มี schema จาก backend แต่ที่ร้ายแรงกว่าคือ **ยังไม่มีใครพูดถึง moderation/spam filter เลย** ก่อนจะออกแบบ UI สาธารณะที่ให้คนพิมพ์ข้อความอิสระบนเว็บ personal branding มันคือช่องให้สแปม, ลิงก์ฟิชชิ่ง, หรือข้อความ offensive โผล่ต่อหน้า HR/ลูกค้าที่เข้ามาดูโปรไฟล์ — ถ้า ship แบบไม่มี rate limit + input sanitization + วิธีลบ/รีวิวก่อนขึ้นจริง (pre-moderation) ความเสี่ยง reputational สูงกว่าประโยชน์ nice-to-have นี้มาก
3. **Overclaim แฝงผ่านการนำเสนอ ไม่ใช่แค่คำพูดตรงๆ** — PROFILE เตือนเรื่อง "อย่า claim ความเชี่ยวชาญที่ยังไปไม่ถึง" และ Brand Strategist เสนอให้เปลี่ยนคำว่า "สนใจ" เป็นคำ active เช่น "กำลังลงมือปรับใช้ AI agents กับงานจริง" — แต่ยังไม่มีหลักฐาน/โปรเจกต์รูปธรรมมารองรับคำนี้เลยในข้อมูลที่มี (Brainstorm ระบุการ์ดโปรเจกต์เป็นแค่ "Nice" ไม่ใช่ "Must") ถ้า ship headline ที่ฟังดู active/ทำจริงแบบนี้โดยไม่มีเคสมารองรับแม้แต่เคสเดียว จะกลายเป็น overclaim ที่แย่กว่าคำว่า "สนใจ" เดิม เพราะมันสร้าง expectation ที่หน้าเว็บพิสูจน์ไม่ได้ — ต้องมีของจริงอย่างน้อย 1 ชิ้นก่อนใช้ถ้อยคำระดับนั้น
4. **นายจ้างปัจจุบัน (จงสถิตย์) ไม่ได้อนุญาต/รับรู้การทำเว็บ personal branding นี้** — PROFILE บอกให้ห้ามเอ่ยชื่อลูกค้า/ข้อมูลลับของบริษัท แต่ไม่มีที่ไหนยืนยันว่า **การเอ่ยชื่อบริษัทเองพร้อมกับเล่าว่า "กำลังเอา AI agents มาปรับใช้กับงานที่ทำอยู่"** ได้รับอนุญาตจากนายจ้างหรือไม่ ถ้า HR ที่มาดูเว็บนี้บังเอิญเป็นคู่แข่ง/พาร์ทเนอร์ของจงสถิตย์ หรือถ้าหัวหน้างานเห็นเว็บนี้ก่อนที่เจ้าตัวจะแจ้ง อาจกลายเป็นปัญหาความสัมพันธ์ในที่ทำงานได้ — ควรถามเจ้าของโปรไฟล์ให้ชัดว่าเอ่ยชื่อบริษัทได้แค่ไหน
5. **Credibility gap ระหว่าง "audience คู่" กับเนื้อหาที่มีจริง** — ทั้ง Brand Strategist และ UX Critic เสนอให้แยกเนื้อหาสำหรับ HR กับลูกค้า แต่ต้นทุนข้อมูลตอนนี้มีแค่ Bio ย่อหน้าเดียวกับ label 3 อัน — การพยายาม "เขียนให้ตอบโจทย์ 2 audience พร้อมกัน" ด้วยข้อมูลบางๆ เสี่ยงทำให้เนื้อหากลายเป็นคำโฆษณาลอยๆ (marketing speak) ที่ไม่มี substance รองรับ ยิ่งพยายาม positioning ให้ดูมืออาชีพเกินตัว ยิ่งเสี่ยง backfire เมื่อ HR ตรวจสอบเพิ่มเติม (เช่น ถาม portfolio ใน interview) แล้วไม่เจอของจริง
6. **Scope creep แฝงในคำว่า "Nice" — โดยเฉพาะ Guestbook + การ์ดโปรเจกต์ + Dark mode** — งานตอนนี้ยังอยู่ Lab 02 (debate) แต่ Brainstorm ผูก Guestbook เข้ากับ "Lab 05 พอดี" ไปแล้วราวกับเป็นข้อสรุป ทั้งที่ยังไม่มีการตัดสินใจ (DECISIONS.md) ว่าจะทำจริงไหม — ความเสี่ยงคือทีมจะเดินหน้าสร้าง backend/DB สำหรับ guestbook โดยอัตโนมัติเพราะ "Lab ถัดไปมันคือเรื่องนี้พอดี" ไม่ใช่เพราะจำเป็นต่อ v1 จริงๆ นี่คือ scope creep ที่ถูกในเบิกทางไว้ล่วงหน้าโดยไม่มีใครตั้งคำถาม
7. **ไม่มี data-retention/deletion policy สำหรับ guestbook หรือ contact form** — ถ้ามีคนกรอกอีเมล/ข้อความส่วนตัวผ่านฟอร์มบนเว็บนี้ (guestbook หรือ contact) ยังไม่มีการพูดถึงเลยว่าเก็บข้อมูลไว้นานแค่ไหน ใครเข้าถึงได้ ลบยังไงถ้ามีคนขอให้ลบ (สิทธิ PDPA/GDPR เบื้องต้น) — สำหรับเว็บสาธารณะที่เก็บ input จากบุคคลที่สาม (ไม่ใช่แค่เจ้าของโปรไฟล์เอง) นี่คือช่องโหว่ด้าน privacy ที่ต้องตอบก่อน ship ไม่ใช่หลัง

### คำถามท้าทายที่ต้องตอบก่อน ship

1. Email plaintext บนหน้า Contact — ยอมรับความเสี่ยงสแปมได้ไหม หรือต้อง obfuscate/ทำฟอร์มกลาง?
2. ถ้าทำ Guestbook จริง ใครเป็นคน moderate ข้อความที่เข้ามา และมี pre-moderation หรือ post-moderation (ลบทีหลัง)?
3. เจ้าของโปรไฟล์ (Tae) ยืนยันหรือยังว่าเอ่ยชื่อ "จงสถิตย์" บนเว็บสาธารณะได้ — ปรึกษานายจ้างแล้วหรือยัง?
4. มีโปรเจกต์/เคสจริงอย่างน้อย 1 ชิ้นที่พร้อมโชว์เป็นหลักฐานรองรับคำว่า "กำลังลงมือปรับใช้ AI agents กับงานจริง" หรือยัง ถ้ายังไม่มี ควรลดโทนคำให้ตรงกับสิ่งที่พิสูจน์ได้จริงตอนนี้
5. Guestbook ผูกกับ Lab 05 แล้วหรือยังในระดับ DECISIONS.md หรือยังเป็นแค่ไอเดียใน Brainstorm — ถ้ายังไม่ตัดสินใจ ห้ามเริ่มออกแบบ schema/DB ล่วงหน้า
6. ถ้ามีฟอร์ม (contact หรือ guestbook) เก็บข้อมูลไว้ที่ไหน นานแค่ไหน ใครลบได้ — มีคำตอบ minimal ที่ทำได้จริงใน scope คอร์สนี้หรือยัง (เช่น auto-purge หลัง N วัน)?
7. ถ้า HR เปิดเว็บแล้วเจอ headline ที่ active/มั่นใจมาก แต่ไม่เจอหลักฐานรูปธรรมเลยสักชิ้น จะเสียความน่าเชื่อถือมากกว่าการใช้คำถ่อมตัวแบบเดิมหรือไม่?

### สิ่งที่ควรตัดออกจาก Must list

Brainstorm ปัจจุบันไม่มี Guestbook/การ์ดโปรเจกต์ใน **Must** อยู่แล้ว (อยู่ใน Nice) ซึ่งถูกต้อง — ข้อเสนอเพิ่มเติมคือให้ตัด/ลดใน Must เอง:

- **"Layout responsive แบบมินิมอล/เอิร์ท ตามตัวอย่างอ้างอิง"** — ควรตัดคำว่า "ตามตัวอย่างอ้างอิง" ออกจากนิยาม Must หรือทำให้ชัดว่าเป็น "แนวทางคร่าวๆ" เท่านั้น (ตามที่ PROFILE เขียนกำกับไว้แล้วว่า "ไม่ต้องเหมือน") เพราะถ้าตีความ Must ตรงตัวเกินไปจะกลายเป็นภาระ design ที่เกินความจำเป็นของ v1
- **Contact ใน Must ควรระบุขอบเขตให้แคบกว่านี้**: "Contact (email + github ที่ให้ไว้)" ควรตัดความคาดหวังเรื่อง contact form/state การเก็บข้อมูลออกจาก v1 โดยชัดเจน (ใช้แค่ mailto/ลิงก์ธรรมดา ไม่มี backend เก็บข้อมูล) เพื่อตัดความเสี่ยง data-retention ข้อ 7 ด้านบนไปเลยในเวอร์ชันแรก — ถ้าจะทำฟอร์มเก็บข้อมูลจริงค่อยยกไปเป็น Nice/Later พร้อม policy ที่ชัดเจนกว่านี้
- **ไม่ควรเพิ่ม "การ์ดโปรเจกต์" เข้า Must แม้จะมีแรงจูงใจจาก Brand Strategist** — ข้อเสนอข้อ 3 ของ Brand Strategist ("ใส่สัญญาณงานจริงลงมาถึง Hero/Interests") น่าสนใจ แต่ต้องยึดว่ายังเป็น Nice จนกว่าจะมีเคสจริงพร้อมโชว์ (ตามคำถามท้าทายข้อ 4) — อย่าปล่อยให้ momentum ของการ debate ดันของออกจาก Nice ไป Must โดยไม่มีของจริงรองรับ
